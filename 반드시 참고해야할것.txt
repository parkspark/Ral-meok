
## 3. 좋은 Goal의 6가지 구성요소

| 구성요소 | 적어야 할 내용 | 예시 |
| --- | --- | --- |
| ① 목표 | 무엇을 완성할 것인가 | 사용자가 부산 행사 정보를 검색하고 저장하는 웹 MVP |
| ② 입력 자료 | 먼저 읽어야 할 파일 | `README.md`, `PLAN.md`, 디자인 이미지 |
| ③ 핵심 기능 | 반드시 작동해야 하는 흐름 | 검색 → 상세 보기 → 즐겨찾기 |
| ④ 제약·비범위 | 바꾸면 안 되는 것과 만들지 않을 것 | 기존 스택 유지, 로그인·결제 제외 |
| ⑤ 검증 방법 | 무엇으로 성공을 증명할 것인가 | 빌드 성공, 테스트 통과, 브라우저 시연 |
| ⑥ 완료 조건 | 언제 작업을 멈출 것인가 | 핵심 흐름 통과 + 오류 없음 + 실행법 문서화 |

### 나쁜 Goal

```
/goal 투두 앱 만들어줘.
```

목표, 범위, 검증, 종료 조건이 없어 에이전트가 임의로 판단해야 한다.

### 좋은 Goal

```
/goal PLAN.md에 정의된 개인 할 일 관리 웹 MVP를 완성하라.

완료 조건:
1. 사용자가 할 일을 추가·완료·삭제할 수 있다.
2. 새로고침 후에도 데이터가 유지된다.
3. 모바일 390px 화면에서 핵심 기능을 사용할 수 있다.
4. npm test와 npm run build가 통과한다.
5. README.md에 실행 방법과 검증 결과가 정리되어 있다.

제약:
- 현재 기술 스택을 유지한다.
- 로그인, 결제, 관리자 기능은 만들지 않는다.
- 기존에 정상 작동하는 기능을 깨뜨리지 않는다.

작업 방식:
- 먼저 현재 프로젝트와 PLAN.md를 읽는다.
- 작업을 작은 체크포인트로 나눈다.
- 각 체크포인트마다 테스트·빌드·브라우저 검증을 수행한다.
- 실패하면 원인을 확인하고 수정한 뒤 다시 검증한다.
- 진행 상황을 짧게 기록한다.
- 완료 조건을 모두 충족할 때만 종료한다.
```

## 4. 바로 복사해서 쓰는 랄프톤 템플릿

아래 대괄호 부분을 팀 내용으로 바꾼 뒤 Codex에 입력한다.

```
/goal 다음 MVP를 완성하라.

## 목표
[누가] 겪는 [어떤 문제]를 해결하는 [서비스 이름/형태]를 만든다.

## 먼저 읽을 자료
- [README.md]
- [PLAN.md 또는 요구사항 문서]
- [디자인·참고 이미지·데이터 파일]

## 반드시 작동해야 하는 핵심 기능
1. [핵심 기능 1]
2. [핵심 기능 2]
3. [핵심 기능 3]

## 만들지 않을 것
- [로그인/결제/관리자 등 이번 MVP에서 제외할 기능]
- [변경하면 안 되는 기존 기능 또는 기술 스택]

## 검증 방법
- 설치: [예: npm install]
- 테스트: [예: npm test]
- 빌드: [예: npm run build]
- 실행: [예: npm run dev]
- 시연: [사용자가 실제로 거치는 핵심 시나리오]

## 완료 조건
- 핵심 기능이 실제 화면에서 모두 작동한다.
- 테스트와 빌드가 통과한다.
- 치명적 오류와 콘솔 오류가 없다.
- 모바일 또는 목표 화면 크기에서 사용할 수 있다.
- README.md에 실행 방법, 구현 기능, 검증 결과가 적혀 있다.
- 발표자가 90초 안에 핵심 기능을 시연할 수 있다.

## 작업 방식
- 먼저 프로젝트를 점검하고 간단한 계획을 세운다.
- 체크포인트 단위로 구현하고 매번 검증한다.
- 실패한 검증은 원인을 수정한 뒤 다시 실행한다.
- 불필요한 대규모 변경은 하지 않는다.
- 진행 상황과 남은 일을 짧게 기록한다.
- 완료 조건을 전부 충족할 때까지 계속한다.
```

## 5. Goal 실행과 상태 확인

### 시작

Codex 입력창에서 `/goal` 뒤에 목표를 입력한다.

```
/goal [목표 + 검증 방법 + 완료 조건]
```

일반 대화로 아이디어를 먼저 다듬은 뒤 다음처럼 요청해도 된다.

```
지금까지 합의한 요구사항으로 Goal을 설정하고 작업을 시작해줘.
완료 조건이 모호하면 시작 전에 필요한 질문만 해줘.
```

### 상태 확인

```
/goal
```

확인해야 할 내용은 네 가지다.

1. 현재 체크포인트
2. 지금까지 검증된 것
3. 남은 작업
4. 막힌 이유와 필요한 조치

### 잠시 멈추기

```
/goal pause
```

목표와 다른 방향으로 가거나, 권한 요청을 검토하거나, 팀이 중요한 결정을 해야 할 때 사용한다.

### 다시 시작하기

```
/goal resume
```

### 목표 종료·초기화

```
/goal clear
```

현재 목표를 완전히 바꾸어야 할 때만 사용한다. 작은 수정이라면 기존 목표의 제약이나 다음 체크포인트를 명확히 하는 편이 낫다.

## 7. 루프를 잘 돌리는 운영법

### 자주 말을 걸기보다 검증 장치를 남긴다

에이전트가 계속 질문하지 않도록 프로젝트 안에 판단 기준을 둔다.

- `PLAN.md`: 목표, 핵심 기능, 비범위, 완료 조건
- `README.md`: 설치·실행·배포 방법
- 테스트 명령: 단위 테스트, 빌드, 린트
- 참고 화면: 디자인 이미지 또는 기대 동작
- 샘플 데이터: 입력·출력 예시

### 진행 상황은 짧게 확인한다

```
현재 체크포인트, 검증 완료 항목, 남은 작업, 막힌 점만 짧게 알려줘.
```

### 막혔을 때는 문제만 풀어준다

좋은 개입:

```
현재 오류의 원인을 먼저 진단하고, 기존 목표와 범위를 유지한 최소 수정으로 해결해줘.
해결 후 같은 검증을 다시 실행해줘.
```

피해야 할 개입:

- 목표와 관계없는 기능을 계속 추가하기
- 전체 구조를 중간에 바꾸기
- 테스트를 건너뛰고 “됐다고 가정”하게 하기
- 에이전트 대신 사람이 코드를 계속 직접 수정하기

## 9. 심사 기준과 Goal 설계 연결

| 심사 항목 | 배점 | Goal에서 보여줄 것 |
| --- | --- | --- |
| 작업지시 | 25점 | 명확한 목표, 요구사항, 비범위, 검증 명령, 완료 조건 |
| 자율수행 | 25점 | 사람의 직접 수정 없이 계획→구현→검증→수정을 수행한 과정 |
| 완성도 | 25점 | 실제 작동 화면, 테스트·빌드 통과, 안정적인 핵심 시연 |
| 창의성 | 25점 | 문제 선택, 아이디어, AI를 활용한 해결 방식의 차별성 |
